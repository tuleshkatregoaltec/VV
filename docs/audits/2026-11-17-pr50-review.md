ARCHITECTURE / INTEGRATION BLOCKERS

1. [P1] Replace local email persistence before enabling this in the deployed service — backend/app/crm/email_store.py:22-56.
Every template, inbound body and send record is read/written as one JSON file guarded only by one process's asyncio.Lock. Both PR and current backend Dockerfiles start TWO workers; production requires multiple API tasks and durable PostgreSQL state. Concurrent workers can reuse ids, overwrite each other's complete snapshots, or race on the same .json.tmp; separate tasks have divergent files and lose history on replacement. A single-worker comment does not match actual runtime. Smallest safe merge: leave this connector disabled/unregistered until persistence is transactional PostgreSQL; merely adding a filesystem lock does not fix task-local durability.

2. [P1] Bind calendar consent to the initiating authenticated browser and consume state once — backend/app/crm/calendar_service.py:47-54,75-81; backend/app/crm/router.py:209-220.
The signed state contains the user/org and PKCE verifier, but callback has no authenticated identity/browser binding or persisted nonce. An attacker can start Connect under their own account, give that Google authorization URL to another person, and have that person's approved Google grant stored under the attacker's VV identity. A state is reusable for 10 minutes with fresh Google codes; membership is never revalidated at completion. Synthetic probe accepted the same state twice (2 commits). Use a server-held single-use nonce plus an authenticated browser/session binding and current membership validation; keep PKCE verifier server-side.

3. [P1] Verify WhatsApp asset ownership before assigning a number to an organization — backend/app/crm/whatsapp/service.py:737-758; backend/app/crm/whatsapp/router.py:191-194.
Any organization owner can enumerate the one global WABA's number ids, then register any id not already present in crm_whatsapp_numbers into their own organization. There is no tenant-specific provider grant, allowlist, or possession proof. Future signed messages for that actual business number are then routed into the claiming tenant by receive_webhook:579-605, and its users can send with the global token. Checking whether another CRM row already owns the number is not provider authorization. Reuse current VV's per-agent Embedded Signup/grant/asset validation instead of adding a second registration path.

4. [P1] Preserve the existing WhatsApp blocked-contact and personal-content boundary — backend/app/crm/whatsapp/service.py:595-614.
This new public signed webhook stores every registered number's message body before any topic classification or blocked-contact check, including personal messages. Current VV explicitly drops blocked contacts before reading text and persists only content-free receipts for unclassified traffic (docs/whatsapp-automation.md:141-151; current migration 7a1d3c5e9b20 clears old unclassified content). The separate crm_whatsapp tables/endpoints bypass the current per-agent connection, contact blocking, disconnect and privacy lifecycle. Route through the existing customer intake or keep this prototype disabled; do not blindly enable parallel ingestion.

5. [P1] Reconcile the incoming migration chain with current VV rather than applying it unchanged — backend/migrations/versions/c3e5a7b9d1f2_add_crm_assistant.py:24; a2d5c7e9f104_add_google_crm_calendar.py:15.
The incoming chain branches at e7b9c1d3f5a2, where current VV continues through WhatsApp releases to 7a1d3c5e9b20, so a straight merge creates multiple Alembic heads. c3e5 additionally alters crm_assistant_messages, whose old creation migration c51b90aa7f42 was deliberately removed from current VV in the shared-assistant reconciliation. That unchanged ancestor is not restored by normal merge, and current databases have the shared assistant tables instead. Keeping c3e5 therefore fails on the missing table even after joining heads. Remove obsolete assistant migration dependency and join only retained compatible connector migrations after current head, preserving deployed files.

CONFIRMED IMPLEMENTATION DEFECTS (IF THESE CONNECTORS ARE RETAINED)

6. [P1] Give Google creates a stable id before any provider request — backend/app/crm/calendar_service.py:280-282,474-492.
POST includes no caller-chosen stable event id, and google_event_id is assigned only after the response. If Google accepts then its response times out, create_event records error; the next calendar load retries POST and creates another event/invitation. Overlapping create/list or two list requests can also push the same pending row twice. Synthetic probe produced [('POST', None), ('POST', None)] for one event after an accepted-but-lost response. Persist a stable valid Google event id and reconcile conflict/unknown outcomes; serialize claims for pending pushes.

7. [P1] Persist and reconcile WhatsApp outbound intent before sending — backend/app/crm/whatsapp/service.py:338-345; backend/app/crm/whatsapp/service.py:654-656.
Agent replies/templates contact Meta before adding/committing their message row. A crash/commit failure after Meta acceptance leaves no durable send record; a lost response is marked failed even though the customer may receive it, encouraging duplicates. A delivery webhook arriving before that commit sees no wamid row and is acknowledged/discarded permanently. Campaign sends have the same callback gap at campaigns.py:431-442. Use a persisted outbound intent and provider callback correlation/durable status inbox, and retain ambiguous outcomes as unknown rather than definite failure.

8. [P1] Order opt-in/out commands by provider event time — backend/app/crm/whatsapp/service.py:620-638.
Incoming timestamps are stored but never used when changing organization-wide suppression. Receiving STOP at timestamp 200 followed by a delayed START at timestamp 100 deletes the newer opt-out and permits promotions again. Independent mock probe printed opted_out=True after STOP and False after the older START. Store the last consent-command timestamp and apply only newer commands atomically; sorting a single webhook batch alone does not handle later requests.

9. [P1] Preserve pending calendar edits when pulling remote events — backend/app/crm/calendar_service.py:409-411,538-543.
After an edit's Google push fails, the row is error/pending with the new local fields. list_events pulls first; _store_google_event unconditionally replaces every local field and marks the row synced before _sync_pending runs. A full sync, or an incremental response containing the old/current remote version, silently loses the edit and prevents retry. Probe changed 'Unsynced local edit'/error into 'Old remote title'/synced. Skip/resolve remote overwrites for pending/error rows and serialize push/pull against the same event.

10. [P2] Calculate reschedule duration before overwriting the old start time — backend/app/crm/router.py:364-379.
The handler assigns event.event_time=payload.time and then uses that new value as original_start. Moving 10:00–12:00 to 09:00 becomes 09:00–12:00 (3h), and moving it to 11:00 becomes 11:00–12:00 (1h). Independent handler probe confirmed the first case; expected 09:00–11:00. Save original time or calculate original interval before mutation, and preserve sub-hour durations rather than forcing a one-hour minimum.

11. [P2] Apply Google changes and exceptions to CRM recurring series — backend/app/crm/calendar_service.py:337-357.
Sync uses singleEvents=true, then drops every expanded instance whose recurringEventId matches a CRM row. Therefore title/time changes made to that recurring series in Google never update CRM, and a cancelled/moved occurrence is ignored before the cancellation branch. CRM continues synthesizing the old schedule. Synthetic changed-title/time instance left 'Old CRM series title'/10:00 unchanged. Sync the series master and its exceptions, or explicitly limit recurrence synchronization instead of reporting synced state while discarding changes.

12. [P2] Include multi-day events that overlap the requested calendar range — backend/app/crm/calendar_service.py:549-552,565.
The API accepts event_end_date but list filtering and in_range use only event_date. An all-day Nov 17–19 event disappears from GET start=Nov18,end=Nov18 even though it is still in progress. Use interval-overlap filtering with the stored end date, and keep recurring occurrence end dates relative to each occurrence (currently only date is advanced at 577-579).

13. [P2] Preserve a newer Brevo webhook state when completing an outbound request — backend/app/crm/email_pipeline.py:289-296.
The queued send is correctly saved before contacting Brevo, so a delivered/opened/bounced callback can run while the provider response is pending. _send_one then blindly sets status='sent' (or failed) and downgrades the webhook's state. Independent probe delivered the callback inside mocked send_email and returned status sent with delivered_at populated. Apply the shared forward-only transition rule when finalizing rather than assigning sent unconditionally.

14. [P2] Recheck current marketing consent immediately before campaign delivery — backend/app/crm/whatsapp/campaigns.py:405-414.
Campaign creation checks consent_status='provided', but send time reloads the contact and checks only do_not_contact and STOP suppression. Changing consent_status to withdrawn while a campaign is queued still sends the promotion. Independent mock probe with withdrawn consent sent once and marked sent. Reuse _why_not against current contact/number/consent at send time; also skip a deleted contact/lead or a recipient whose current phone no longer matches the captured wa_id.

15. [P2] Make delivery status advancement atomic across webhook requests — backend/app/crm/whatsapp/service.py:643-661.
Two workers can select the same message at sent, independently decide read and delivered both advance, then commit read first and delivered last. The last write regresses the persisted state, despite the forward-only invariant and sequential test coverage. SELECT FOR UPDATE scoped to the message or a rank-conditional atomic UPDATE fixes this. Also constrain the status's phone_number_id to the matched message.number_id, rather than only checking both ids separately exist.

16. [P2] Enforce one active campaign number in the database — backend/app/crm/whatsapp/service.py:719-735; backend/migrations/versions/b7d2e9f4a1c3_add_crm_whatsapp.py:42-49.
The limit is a count-then-insert guard only. Two owners concurrently registering different campaign ids both observe count=0 and commit because the only partial unique index covers agent numbers. campaign_number then picks an arbitrary .first(), splitting campaign inboxes and making another sender's replies disappear. Add a partial unique index on organization_id WHERE active AND purpose='campaign' and translate its conflict to 409.

17. [P2] Exclude unsupported template components or send their required parameters — backend/app/crm/whatsapp/meta.py:193-208,165-169.
list_templates exposes every approved template but retains only BODY text; outbound payload can supply only BODY text params. An approved template with a dynamic text/media HEADER or URL button is offered as sendable, passes the local body-param count, then fails at Meta because the mandatory header/button arguments were dropped. Preserve/render those components or filter to the body-only templates this API supports. Current tests cover only body-only templates.

18. [P2] Suppress subsequent email sends after unsubscribe or spam feedback — backend/app/crm/email_pipeline.py:334-350; backend/app/crm/brevo.py:68-71.
The connector explicitly sends marketing/news to CRM leads and records unsubscribed/spam events, but feedback changes only one send's status. send_emails checks only the unchanged PostgreSQL contact.do_not_contact flag, so the next bulk send still posts to Brevo for that address. Maintain organization/address suppression from unsubscribe/complaint feedback and enforce it on every send; events on one record are not a contact suppression mechanism.

19. [P2] Do not trust a guessable reply id to identify a customer/tenant — backend/app/crm/email_pipeline.py:527-536,573-575.
An arbitrary external sender can send to reply+<sequential send id>@configured-domain. The signed Brevo webhook authenticates the provider, not the email author; _send_for_reply accepts the id without checking mail.from_email against send.to_email, then assigns the victim send's organization/enquiry and marks it replied. This permits unrelated mail to be injected into another lead/tenant's conversation. Use an opaque unguessable signed routing token and validate sender/thread ownership before associating the lead; keep unmatched mail unlinked.
